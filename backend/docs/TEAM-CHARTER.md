# BTCBOX 三团队协作总章程

版本：1.0  
生效日期：2026-11-02  
适用范围：BTCBOX 全部前端产品工作、共享规范、集成和验收  
唯一原则：三组各做自己的事，彼此监督但不越权执行。

## 1. 组织结构

| 编号 | 团队 | 角色 | 核心问题 |
|---|---|---|---|
| 1号 | Visual Team（视觉组） | 视觉总监 / UI | 长什么样 |
| 2号 | Interaction Team（交互组） | UX 架构师 | 怎么操作 |
| 3号 | Business Team（功能组） | 业务工程负责人 | 能不能真实使用 |

三组保持专业职责与文件owner边界。当前执行周期由1号牵头全站视觉与前端工作节奏；2号作为独立复核与交互修复伙伴；3号负责真实业务和数据实现；项目协调者负责跨团队总管、风险与验收。牵头权不改变专业owner，也不授权越过业务、安全和用户锁定规则。允许并行工作，但必须遵守共享规范、接口契约和文件责任边界。

## 2. 两个公共层

### 公共层 A：统一规范库

位置：`docs/`。

所有团队共同读取的规则、产品约束、接口契约、验收标准、问题记录、工作日志和交接记录均放在这里。

- `TEAM-CHARTER.md`：三组组织章程与边界。
- `AI-CORE.md`：项目最高执行约束。
- `AI-TEAM-START-HERE.md`：所有 Agent 的入口。
- `AI-1-TASK.md` / `AI-2-TASK.md` / `AI-3-TASK.md`：各组唯一任务书。
- `AI-INTERFACE-CONTRACT.md`：三组交界处的公共接口。
- `AI-TASK-BOARD.md`：任务与进度。
- `AI-CHANGELOG.md`：实际变更记录。
- `AI-COMMUNICATION.md`：跨组监督意见和通知。
- `AI-ISSUE-LOG.md`：缺陷、疑问、建议。
- `AI-HANDOFF.md`：中断与恢复。
- `ACCEPTANCE-SCORECARD-v1.0.md`：统一验收评分表。

三组必须读取公共规范，不得各自建立互相冲突的“私有标准”。规范修改由项目协调者根据用户明确指示维护；团队可以提出修改建议，不得单方面改写共同规则。

### 公共层 B：共享技术基础层

位置：`src/`。

目标目录：

```text
src/
├── api/          # API 客户端、请求适配、错误映射
├── store/        # 全局状态、数据缓存、状态同步
├── router/       # 路由注册、守卫、跳转契约
├── layouts/      # 页面框架、导航和内容布局
├── components/   # 全站共享 UI 组件
├── hooks/        # 可复用交互与数据 hooks
├── utils/        # 通用工具
├── types/        # API、领域、组件和状态类型
└── constants/    # 业务常量、状态常量和共享常量
```

重要：当前仓库真实运行架构仍以 `index.html`、`assets/js/`、`assets/css/` 为主，`src/` 是目标公共技术架构与契约层。不得为了“看起来模块化”而搬迁现有代码、创建未接入构建的假模块或破坏当前 SPA。迁移必须先由三组提出方案、核对依赖和构建入口，再单独批准执行。

### src 子目录责任

| 目录 | 主责 | 其他团队边界 |
|---|---|---|
| api | 3号 | 2号定义交互所需调用时机；1号不得改变请求契约 |
| store | 3号 | 2号定义用户可见状态流；1号定义状态视觉映射 |
| router | 2号 | 3号负责权限/会话数据契约；1号负责导航外观 |
| layouts | 1号 | 2号定义布局内的操作流程；3号提供真实数据 |
| components | 1号 | 2号定义交互行为契约；3号提供业务数据接入 |
| hooks | 按子模块分责 | `hooks/interaction` 归2号；`hooks/data` 归3号；共享视觉 hook 归1号 |
| utils | 按用途分责 | 视觉格式化归1号；交互工具归2号；数据/业务工具归3号 |
| types | 3号 | 2号可提出交互状态类型需求；不得私自改变公共类型 |
| constants | 3号 | 设计 token 仍由1号在设计系统中维护；交互常量由2号提出并登记 |

共享目录中的每个具体文件仍必须在接口契约或任务板中指定唯一主责人。目录主责不等于其他团队可以直接改写该目录。

## 3. 三组职责与禁止越界

### 1号 Visual Team — 视觉组

负责：
- 品牌风格、色彩体系、字体体系、图标体系。
- Design Tokens、Dark Mode、主题、间距、圆角、阴影。
- 页面视觉布局、信息层级、桌面/移动端视觉构成。
- 共享组件的外观、尺寸、状态样式。
- 表格、卡片、按钮、输入框、弹窗、抽屉、图表区域的视觉呈现。
- 对标 Binance / OKX / Bybit / Coinbase 的视觉完成度。

交付：
- Design System。
- Color Tokens、Typography、Icons、Layout、Theme、UI Components。
- 页面视觉规范和视觉验收证据。

不得：
- 改变按钮实际业务动作、API 请求、路由业务含义或数据状态。
- 自行决定何时提交订单、何时扣款、何时校验余额。
- 用视觉效果伪装不存在的业务能力或真实成功状态。
- 擅自更换用户批准的字体、官方 Logo、品牌规则。

### 2号 Interaction Team — 交互组

负责：
- 用户流程、页面跳转、操作顺序、返回路径。
- 表单交互、输入校验的体验编排、确认流程。
- Loading / Success / Error / Warning / Empty / Disabled / Restricted 状态的触发规则和反馈时机。
- Modal / Toast / Drawer 的使用时机、关闭规则、焦点与键盘交互。
- 动效、状态切换、价格闪烁、成交反馈、深度图联动、K线缩放等体验规则。
- WebSocket 状态变化对用户体验的表现要求和恢复提示。
- 路由交互、用户操作流程和可用性。

交付：
- 用户流程图、状态机、交互契约、异常与反馈矩阵、路由流程说明。

不得：
- 实现或改变撮合、余额、账本、费用、权限等业务规则。
- 修改 API 请求/响应结构、数据库或服务端。
- 仅凭 UI 推断数据成功；成功状态必须由3号提供的真实业务结果触发。
- 为了流程顺畅而跳过安全校验、确认步骤或限制状态。

### 3号 Business Team — 功能组

负责：
- 真实业务能力、API 对接、数据处理、状态管理。
- 用户登录、注册、会话、权限和 KYC 数据接入。
- 钱包、资产、充值、提现、划转、理财数据。
- 行情、WebSocket 连接和数据订阅。
- 现货、合约、秒合约、订单、成交、持仓数据。
- API / Store / Types / Constants / 数据类 hooks。
- 数据正确性、错误码映射、重连和重复请求保护。

交付：
- 可验证的业务功能、API/数据契约、状态数据源、错误映射和测试证据。

不得：
- 自行决定视觉样式、组件布局或用户流程。
- 用假数据、假成功或静态数字冒充真实业务。
- 未经明确授权改动数据库、资金账本、撮合、结算、认证安全策略、生产密钥或部署配置。
- 为迁就视觉效果而改变金额精度、数据含义、业务校验或接口语义。

## 4. 团队间监督方向（严格单向）

监督方向固定：

- 1号 → 2号：只审查交互流程、操作反馈、状态转换是否清楚、完整、一致。
- 2号 → 3号：只审查业务功能、API 数据、状态同步、异常处理是否符合交互契约且真实可靠。
- 3号 → 1号：只审查视觉规范、组件、布局、响应式和设计系统是否满足产品标准并能正确呈现真实状态。

监督者只能：
1. 指出可定位的问题。
2. 给出证据和复现步骤。
3. 引用违反的规范或接口契约。
4. 提出建议方案和风险。
5. 将意见写入 `AI-ISSUE-LOG.md`，必要时写入 `AI-COMMUNICATION.md`。

监督者不得：
- 直接修改被监督团队的文件或分支。
- 替对方实现修复、接管任务或改变对方优先级。
- 因对方尚未处理建议而停止自己的工作。
- 反复争论个人偏好或将建议当成强制命令。
- 以监督名义修改公共规范。

被监督团队负责自行评估意见、决定处理方式、实施修改并记录理由。涉及用户已批准的硬性规范、P0/P1 缺陷或一票否决项时，必须整改或升级协调，不得以“建议”为由忽略。

## 5. 交付边界与共同接口

每个跨组功能必须明确三份契约：
- Visual Contract：组件外观、尺寸、布局、状态视觉。
- Interaction Contract：用户流程、事件、状态机、反馈时机。
- Business Contract：数据字段、API、业务状态、错误语义和权限边界。

示例：下单
- 3号提供真实余额、交易规则、订单提交结果和订单状态。
- 2号定义输入、校验提示展示、确认、加载、失败/成功反馈流程。
- 1号定义表单、买卖按钮、盘口、状态标签和订单结果的视觉表现。

任何一方不得伪造另外两份契约。

## 6. 工作记录要求

每个团队每次实质工作必须记录：
- 团队编号、日期、分支、开始 SHA、当前 SHA。
- 修改文件及修改原因。
- 完成事项与未完成事项。
- 实际运行的命令、测试结果和浏览器证据。
- 发现的问题、未知项、风险。
- 对其他团队提出的监督意见及其 Issue ID。
- 下一步唯一明确动作和中断恢复位置。

计划不等于完成；代码存在不等于测试通过；源代码检查不等于浏览器验证。

## 7. 验收与发布

统一使用 `ACCEPTANCE-SCORECARD-v1.0.md`：
- 功能组 50 分。
- 交互组 30 分。
- 视觉组 20 分。
- 总分至少 85 分，且没有任何一票否决项，才达到本评分表的上线门槛。
- 任何一票否决项触发，直接禁止上线，不以总分抵消。
- Binance 对标审核是附加对标项，不另加分、不替代实际功能测试。
- 未经用户明确授权，不得合并到生产主分支或部署生产环境。

## 8. 冲突优先级

1. 用户明确指令。
2. 资金、账户安全和数据真实性。
3. 本章程及统一公共规范。
4. 三份接口契约。
5. 各团队任务书。
6. 个人实现偏好。

发现冲突，只暂停冲突部分，记录证据和建议；其他不冲突工作继续推进。


## 9. User-directed operating leadership update — 2026-11-02

1号牵头为主，2号复核修复，协调者总管大局：

- **1号 — Project Execution Lead（前端执行牵头）**：制定全站视觉方向、页面推进顺序、设计系统和跨团队交付节奏；汇总1号视觉实现与3号业务依赖。牵头不代表可更改业务规则、API语义、资金安全策略或用户锁定布局。
- **2号 — Independent Review & Repair（独立复核与修复）**：主动检查1号的页面与组件交付、检查端到端操作体验；直接修复2号owner范围内的问题。涉及1号/3号owner文件时，先写明证据、风险和建议，协调owner后再行动；不得无声覆盖对方改动。
- **3号 — Business Delivery Owner（业务交付负责人）**：继续负责API、Store、行情、账户、钱包、订单和真实业务数据；按照1号整体推进节奏提供依赖和交付。业务规则与受保护资金/认证/安全边界仍由业务owner管理，重大受保护变更仍须用户明确授权。
- **Coordinator — Overall Governance（总协调/总验收）**：跟踪所有分支、任务板、问题日志、CI、测试、依赖和风险；协调优先级、解决跨组阻塞、执行最终独立验收。不得以文档或静态检查代替实际测试。
- 具体文件仍只有一个 primary owner。执行牵头、复核职责不等于取得对方文件的默认写权限。
- 工作节奏：1号提出整合批次 → 2号独立复核并修复owner范围问题 → 3号交付业务依赖 → Coordinator检查整体一致性与验收证据。安全、数据真实性和锁定交易页要求优先于进度。
