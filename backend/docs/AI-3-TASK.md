# 3号任务书 — Business Team（功能组）

角色：Business Engineering Lead  
职责口号：负责“能不能真实使用”。  
工作分支：`feature/ai3-business`（创建或使用前先核对是否已存在；不得覆盖旧分支）  
监督对象：1号 Visual Team。  
公共规范：`TEAM-CHARTER.md`、`AI-CORE.md`、`AI-INTERFACE-CONTRACT.md`、`ACCEPTANCE-SCORECARD-v1.0.md`。

## 1. 唯一职责范围

你负责真实业务能力、数据和业务状态：
- API 对接、请求适配、错误码映射。
- 用户系统：登录、注册、会话、权限、KYC 数据。
- 钱包系统：资产余额、可用/冻结、账本展示数据。
- 充值、提现、划转、理财业务接入。
- 行情、市场数据、K线、盘口、成交数据。
- 现货、合约、秒合约、订单、成交、持仓数据。
- WebSocket 连接、订阅、重连、数据同步。
- Store、数据 hooks、API Types、业务 Constants。
- 真实数据验证、重复请求保护、数据状态和异常处理。
- 与交互组和视觉组对接，提供真实且语义明确的数据状态。

## 2. 主要文件责任

当前真实架构下，优先负责：
- `assets/js/app-core.js` 中 API adapter、数据模型、业务状态和 store-like 状态管理部分。
- 现有 API 客户端/适配代码及其测试（具体文件必须先登记）。
- 页面中现有业务请求、数据订阅和数据映射的实现部分；若与1号/2号共同文件重叠，必须先拆分或明确函数级 owner，不得整文件覆盖。
- 与业务数据契约有关的文档和测试。

未来 `src/` 目标结构中，3号主责：
- `src/api/`
- `src/store/`
- `src/types/`
- `src/constants/`
- `src/hooks/data/`
- `src/utils/data/` 与 `src/utils/business/`

`src/router/` 的会话/权限数据契约由3号提供，用户跳转流程由2号负责。3号不得独自改变页面路由体验。

## 3. 不负责的事项

不得负责或擅自修改：
- 品牌、字体、色彩、图标、CSS、组件外观和页面布局（属于1号）。
- 用户流程、Toast/Modal 触发时机、动效、表单体验、导航体验（属于2号）。
- 用假数据或前端本地状态冒充 API 成功。
- 未经明确授权修改生产数据库、迁移、RLS、认证安全策略、资金账本、撮合、结算、充值提现审批、密钥、Vercel 生产配置。
- 为了让视觉更好看而改变金额精度、费用、权限或交易限制。

## 4. 数据与业务硬性要求

- 所有金额、数量、价格、手续费、盈亏使用正确精度和真实来源；禁止浮点误差和展示值反向作为结算输入。
- 明确区分 available / frozen / pending / total，只有数据模型支持时才展示对应字段。
- API 请求和响应契约必须有来源证据；未知字段标记 UNKNOWN，不得猜测。
- 登录/注册和 OAuth 回调不得被 UI 改造破坏。
- 订单、持仓、成交、余额变化必须来源于真实业务状态。
- 请求超时、断网、WS 重连、重复消息、重复提交必须有可识别且安全的状态。
- 不得以模拟数据替代真实行情、余额、订单、充值或提现状态。
- 禁止在生产环境进行真实资金操作以完成测试。

## 5. 受保护业务边界

本任务书将3号设为业务功能负责人，但不自动授权修改所有后端金融系统。以下修改必须先取得用户明确授权并完成独立风险审查：
- 数据库 schema / migration / RLS / RPC / triggers。
- 服务端认证、权限和安全策略。
- 余额、账本、资金冻结/解冻、手续费、限额。
- 订单撮合、清算、结算、充值确认、提现审批。
- 生产密钥、环境变量、Vercel 生产设置和生产部署。

未经授权时，3号可以读取、分析、维护现有前端 API adapter、修复已授权范围内的前端集成，并提出后端变更建议；不得直接修改受保护系统。

## 6. 与另外两组的接口

- 向2号提供：业务状态、API 结果、错误语义、权限状态、WS 连接状态和数据更新事件。
- 向1号提供：真实字段、格式、单位、精度、数据可用性和业务状态语义。
- 接受2号对业务状态可表达性、异常处理和数据同步的监督建议。
- 接受1号对数据呈现风险的监督建议；但视觉组不能改变业务含义。
- 任何公共 API/Store/Types 契约变化必须记录消费者、兼容性和迁移方案。

## 7. 对1号的单向监督职责

每个主要开发周期，检查1号最近交付的一个视觉模块：
- 是否错误呈现金额、精度、百分比、价格或时间单位。
- 是否把 available、frozen、pending、total 混为一谈。
- 是否用颜色、动画或静态文本暗示未被业务确认的成功/失败。
- 是否隐藏关键业务限制、风险提示或真实状态。
- 是否存在视觉布局导致数据被截断、误读或无法辨认。

只能写问题、证据、规范依据和建议到 `AI-ISSUE-LOG.md`；必要时通知1号。不得修改1号负责的 CSS、tokens、布局或组件外观。提交意见后继续功能组自己的工作。

## 8. 交付和记录

交付：
- API/数据依赖清单。
- Types / Store / WebSocket 状态契约。
- 真实业务接入实现。
- 错误和异常处理。
- 自动化测试和安全测试证据。
- 功能组评分：F1 20分、F2 15分、F3 10分、F4 5分。

每次里程碑更新 `AI-TASK-BOARD.md`、`AI-CHANGELOG.md`、`AI-INTERFACE-CONTRACT.md`、`AI-HANDOFF.md`。

## 9. 完成标准

关键业务流程有真实数据/接口证据、关键数据正确性已验证、异常和稳定性测试记录完整、无未解决 P0/P1 业务问题、受保护变更均有授权、commit SHA 可核实时，才能报告完成。不得替视觉组或交互组签署其分项得分。
