# Financial Operation Contract — Round 57

## Purpose

This round establishes shared validation primitives and a repeatable source-level inventory. It does **not** route any live balance-changing endpoint through the new helpers. The active `server.py` still uses JSON state, so partial route integration is intentionally deferred until the DB schema/RPC and all call sites are reviewed together.

## Shared contract

- Monetary inputs must be decimal strings, integers, or `Decimal`; binary floats are rejected.
- Amounts must be finite, non-negative, within the supported magnitude and within the explicitly configured decimal scale. Operations requiring a positive amount use the default `allow_zero=False`.
- Asset symbols are normalized to uppercase and validated against `[A-Z0-9]{2,16}`.
- Idempotency keys must be caller-provided stable identifiers with a minimum length of 8 characters; DB RPCs may impose stricter limits (current SQL commonly requires 16 characters). Use the stricter intersection at API boundaries.
- Request fingerprints include operation, actor, normalized asset, exact decimal amount, and a business reference for withdrawal review, deposit confirmation, and earn redemption. Never include passwords, tokens, or unnecessary PII.
- Lifecycle transitions are explicit and terminal states cannot be reopened by the shared contract.

## Source inventory

`FINANCIAL-WRITER-INVENTORY.json` is generated by `scripts/audit_financial_writers.py`. It parses `server.py` as Python AST without executing it and records assignment targets containing `balances` or `frozen`.

The inventory is a source-level lead list, not a complete proof: dynamic mutation helpers, dictionary updates, aliases, reflection, or mutations hidden behind calls may evade this simple scanner. Review every hit manually and search for `save_data`, balance-like fields, admin adjustment endpoints, rewards, referrals, fee/rebate logic and future plugins before cutover.

## Critical known paths

- `do_order`: simulated spot order and two-asset balance movement.
- `do_withdraw`: available-to-frozen movement plus pending withdrawal creation.
- `admin_review_withdraw`: release frozen funds and possibly restore available funds.
- `admin_confirm_deposit`: credit balance after manual confirmation.
- `do_GET` admin adjustment: direct query-string balance mutation; this is particularly risky and should be replaced by an authenticated, CSRF-protected POST with reason, actor identity, idempotency key and immutable audit record before production use.
- `do_POST` earn subscribe/redeem: debit/credit plus position state mutation.
- `load_data`: legacy compatibility migration for the `frozen` field, which must be kept distinct from the business frozen-balance bucket.

## Required API/RPC semantics before wiring routes

1. Derive actor identity from server-side authenticated context, never request body alone.
2. Validate authorization and operation-specific state transition before attempting a write.
3. Use one database transaction for account changes, business record changes, ledger rows, and audit records.
4. Persist a unique idempotency key plus canonical request fingerprint. Same key/same fingerprint returns the original outcome; same key/different fingerprint is a conflict.
5. On network timeout, report unknown outcome and retry with the exact same key; do not invent a new key.
6. Amount and fee calculation use decimal/numeric types, never float arithmetic.
7. Do not treat simulated orders as exchange executions or admin deposit confirmation as chain verification.

## Test boundary

Unit tests validate the Python contract and source inventory only. They do not establish database locking, RLS, RPC grants, transactional rollback, multi-instance concurrency, or production safety. Those require a dedicated staging database and a reviewed test plan.
